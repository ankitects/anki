翻訳、デッキ、アドオンなど、コード以外の貢献については[貢献ガイド](/manual/contrib)をご覧ください。

## 協力を募集しています

貢献したいものの、何に取り組めばよいか分からない場合は、Anki リポジトリの GitHub の[Issue 一覧](https://github.com/ankitects/anki/issues)をご覧ください。

## 大規模な変更

大規模な変更、特に Issue トラッカーに記載されていない変更に取りかかる前に、フォーラムで相談してください。受け入れられる可能性を事前にお伝えできます。多くの時間をかけたプルリクエストが却下されると、双方にとって残念な結果になります。

## まずアドオンで実現できないか検討する

新機能のプルリクエストを送る前に、アドオンとして実装できないか検討してください。Anki 本体のコードベースは、できるだけ小さく保ち、保守しやすくする方針です。多くの優れたアイデアはアドオンにする方が適しています。より速く改善でき、すべてのユーザーに影響を与えずに特定のニーズに応えられます。

アドオンの作成方法については、[アドオン API のドキュメント](https://addon-docs.ankiweb.net/)をご覧ください。

## プルリクエストの説明

プルリクエストを作成するときは、用意されているテンプレート（`.github/pull_request_template.md`）に記入してください。関連する Issue、概要と動機、テスト方法、UI に視覚的な変更がある場合の証拠など、必要な項目が記載されています。

## 関連する Issue

緊急修正と依存関係の更新を除き、すべてのプルリクエストを既存の未解決 Issue に紐付けてください。該当する Issue がない場合は、プルリクエストを送る前に問題を説明する Issue を作成してください。適切な問題を解決していることを確認し、双方の無駄な作業を防ぐためです。

関連 Issue のないプルリクエストは、短期間後に自動で閉じられる場合があります。

## 依存関係の更新

Dependabot のプルリクエストには、関連 Issue は不要です。レビューや取り込みの際は[Dependabot の更新手順](/developers/dependabot)に従ってください。

## リファクタリング

リファクタリングを主な目的とするプルリクエストは避けてください。すべてのプルリクエストにはレビューのコストがかかり、意図しない不具合を持ち込む可能性もあります。コードが少し洗練されるだけでは、こうしたコストに見合わないことがよくあります。

リファクタリングに価値がないという意味ではありません。同じ箇所を扱うプルリクエストの一部として行う方が適しています。たとえば、バグ修正に伴う小さな変更や、新機能の導入に伴う大規模なリファクタリングです。

## 型ヒント

Anki の Python コードの大半には型ヒントがあり、コード補完が改善され、開発中にエラーを見つけやすくなります。新しいコードを追加する場合も型ヒントを記述してください。記述しないとテストに失敗します。

Qt のスタブは完全ではないため、`cast()` を使ったり、型エラーを無視したりする必要がある場合があります。シグナルを接続する場合は、`aqt.utils` にある `qconnect()` ヘルパーを使うと、変数名の誤りなどほかのエラーを隠さずに型の警告へ対処できます。

互いを参照する2つのモジュールがある場合は、型に完全修飾名を使い、アノテーションを有効にすると、循環インポートを解消できます。たとえば、次のコードではなく

```
from aqt.browser import Browser

def myfunc(b: Browser) -> None:
  pass
```

次のようにします。

```
from __future__ import annotations

import aqt

def myfunc(b: aqt.browser.Browser) -> None:
  pass
```

## フック

アドオンを作成していて、現在フックがない関数を拡張したい場合は、必要なフックを追加するプルリクエストを歓迎します。プルリクエストに用途を記載していただけると助かります。

フック名は、次のいずれかの形式に沿うようにしています。

[対象] [動詞] - 例: `note_type_added`、`card_will_render`

[モジュール] [動詞] [対象] - 例: `browser_did_change_row`、`editor_did_update_tags`

Qt のコードでは、特定の画面に関するフックが多いため、2つ目の形式がよく使われます。pylib のコードでは、カードやノートなどの対象に焦点を当てるため、1つ目の形式がよく使われます。

過去形の `changed` の代わりに `did change` を使うと不自然に感じるかもしれませんが、`will` と形式をそろえられ、iOS のライブラリで使われる命名方法にも似ています。

多くの場合、フックは pylib より GUI のコードに追加する方が適しています。

フックのコードは `pylib/tools/genhooks.py` と `qt/tools/genhooks_gui.py` の定義から自動生成されます。どちらかのファイルに新しい定義を追加すると、生成ファイルが更新されます。

既存のフックに引数を追加するなど、変更する場合は、後方互換性を保つために既存のフックをそのまま残してください。名前の似た新しいフック定義を作成し、新しいフックの定義に `replaces="name_of_old_hook"` と `replaced_hook_args=["..."]` を指定します。古いフックに旧形式のフックがある場合、新しいフックの定義に旧形式のフックを追加しないでください。

## 翻訳

Anki に翻訳可能な文字列を追加する方法は、[翻訳ガイド](/translators/anki/developers)をご覧ください。

ドキュメントの翻訳方法は、[マニュアルの翻訳](/translators/anki/manual)をご覧ください。

## テストを通す

コードを提出する前に、`ninja check` が正常に完了することを確認してください。

Git フックからこのチェックを実行するには、[pre-commit](https://pre-commit.com/)を使います。リポジトリのルートにある `.pre-commit-config.yaml` で設定されています。開発用の依存関係をインストールした後（例: `uv sync --group dev`）、次のいずれかを実行します。

```
uv run pre-commit install --hook-type pre-push
```

```
python3 -m pre_commit install --hook-type pre-push
```

（`pre-commit` 実行ファイルが PATH にある場合、たとえば `pip install --user pre-commit` 後や仮想環境を有効にした場合は、`pre-commit` のみでも実行できます。）

同梱のフックは、すべてのチェックに時間がかかるため、コミットごとではなく **pre-push** 時に `./ninja check` を実行します。必要に応じて、いつでも手動で `./ninja check` を実行できます。

`ninja` などのツールを標準以外の場所にインストールしている場合は、普段使うシェルの `PATH` がフックから参照できることを確認してください。pre-commit はログインシェルを使わないため、PATH の違いで余分な再ビルドが起きる場合があります。

新しい動作や変更した動作は、テストで確認してください。テストが不要な例外は、バージョン更新、ドキュメントのみの変更、翻訳の更新、依存関係の更新、CI/ビルドの保守作業（chore）です。

## コードスタイル

新たに追加するコードでは、Python 標準の snake_case 形式の変数名と関数名を使ってください。既存の関数名を変更する場合、アドオンがその関数名に依存していることが多いため、古い関数名のエイリアスも追加してください。

## 1つの変更に絞る

パッチやプルリクエストは、1つの問題を解決するために必要な最小限の変更にしてください。無関係な変更をまとめたプルリクエストはレビューが難しく、却下されるため、別々に分けてください。

## AI を使った貢献

コードの作成やレビューに AI ツールを使うことは認められています。ただし、提出する変更をすべて理解している必要があります。変更内容とコードベースへの影響を説明できない場合、プルリクエストは閉じられます。

AI が生成したコードは慎重にレビューしてください。人による確認なしで提出されたように見えるプルリクエスト（無関係なコード、重複したロジック、実装と合わないコメントなど）は、追加の議論なしに閉じられる場合があります。
