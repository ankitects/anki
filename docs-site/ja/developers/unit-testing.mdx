title: "Anki のユニットテストを書く"
---

このガイドでは、Anki のメンテナー、コントリビューター、コーディングアシスタント向けに、ユニットテストとコンポーネントテストの書き方を説明します。特定の機能、モジュール、バグに依存しない内容です。変更対象の動作、周辺の本番コード、近くにあるテストと合わせて利用してください。

自動テストの基本を理解していることを前提としています。テストが初めての場合は、[参考資料](#参考資料と背景)にある入門資料を読んでから、Anki 固有の説明に戻ってください。

## 要約

テストを追加するときは、次の点を意識します。

1. ユーザーの視点で、期待する動作を説明する。
2. その動作を担うコードの近くにテストを置く。
3. 通常の入力、エラー、境界条件、既知の回帰を検討する。
4. 十分な確信を得られる、最小かつ高速なテストを選ぶ。
5. 確認する動作が分かる名前を付ける。
6. 実時間、ネットワーク、ユーザーデータ、テストの実行順序に依存させない。
7. バグ修正では、可能なら修正前にテストが失敗することを確認する。
8. 関連する `just test-*` レシピを実行し、その後 `just check` を実行する。

## 目的

有用なテストは、重要な動作について、迅速で信頼できる根拠を示します。また、実行可能なドキュメントとしても機能します。読み手が実装を逆解析しなくても、シナリオ、操作、期待結果を理解できるようにしてください。

優れたユニットテストには、次の性質があります。

- **動作を検証する:** 観測可能な結果、状態遷移、エラー、必要なやり取りを確認する。
- **焦点が明確:** 失敗する理由が1つである。1つの動作を説明する複数のアサーションは問題ありません。
- **決定的:** 同じコードと入力なら、テスト順序、時刻、ロケール、ネットワーク、マシン速度にかかわらず同じ結果になる。
- **分離されている:** ユーザープロファイル、別のテストの状態、利用できない外部サービスに依存しない。
- **高速:** 編集中に繰り返し実行できる。
- **読みやすい:** 名前とテストデータから、期待される動作と失敗内容が分かる。
- **不具合を検出できる:** 実際に回帰があれば失敗し、期待する動作が壊れても通り続けることがない。
- **安定している:** 動作を保つリファクタリングでは、通常は変更せずに済む。

コードカバレッジは未テストのコードを見つけるのに役立ちますが、行が実行されたからといって動作が検証されたとは限りません。カバレッジの数値を上げるだけの弱いアサーションを追加しないでください。

## 有用な最小のテスト境界を選ぶ

動作を証明できる、最もコストの低いテストを選びます。

| 境界 | 用途 | 避ける用途 |
| --- | --- | --- |
| 純粋なユニットテスト | 計算、解析、検証、変換、決定的な状態遷移 | フレームワークの配線やプロセス間の動作 |
| 依存要素を含むユニットテスト | 少数の高速なインプロセス依存要素 | ネットワーク、実プロセス、ユーザーの永続データ |
| UI コンポーネント | Qt の表示状態、シグナル、イベント、操作。Svelte では抽出したロジックとストア | アプリ全体のワークフロー |
| 統合テスト | DB マッピング、protobuf/言語ブリッジ、ファイルシステム契約、ユニットテストで証明できないフレームワーク連携 | ユニットレベルの分岐をすべて繰り返すこと |
| エンドツーエンド | 実際の Anki とブラウザーを使う、重要なワークフローを少数検証 | 網羅的な検証や境界条件の列挙 |

ほとんどのシナリオはエンドツーエンドより下の層で扱います。上位のテストで不具合が見つかった場合、再現可能なら下位層に回帰テストを追加してください。上位のテストは、追加の動作を証明できる場合に残します。

Svelte の「UI コンポーネント」は、抽出したロジックとストアを指します。現状、リポジトリのユニットテストには描画済みコンポーネントのテスト環境が組み込まれていません（[Svelte、TypeScript、JavaScript](#svelte-typescript-javascript)を参照）。

Anki は複数の実装層にまたがります。ルールを所有する層でテストしてください。

- Rust で実装されたビジネスルールは、通常 Rust でテストします。
- Python ライブラリのテストでは、Python が所有する動作、互換性のあるインターフェース、オーケストレーション、適応処理を確認します。Rust の検証を重複させないでください。
- Python/Qt のテストでは、GUI が所有する状態、シグナル、コールバック、バックエンドのオーケストレーションを確認します。実用的であれば、フレームワークに依存しないロジックを、GUI 全体を構築せずにテストできる形にします。
- TypeScript/JavaScript のテストでは、Web 側が所有するロジック、ストア、DOM ヘルパー、コンポーネント動作を確認します。実際のブラウザーと Anki の境界が不可欠な場合だけエンドツーエンドテストを使います。
- 生成された protobuf コードにテストは不要です。独自の変換、検証、ブリッジ動作は所有する層でテストし、両側に依存する正しさには統合テストを使います。

## 期待する動作からシナリオを選ぶ

テストコードを書く前に、期待する動作を平易な言葉で説明します。入力、呼び出し側またはユーザーが観測できる結果、副作用、エラー、維持すべき事実を特定します。そのうえで、正しい実装と、もっともらしいバグのある実装を区別できる最小のシナリオを選びます。

意味のある動作変更では、次の観点を検討します。

| 分類 | 確認すること | 一般的な例 |
| --- | --- | --- |
| 正常系 | 代表的な有効入力から意図した結果が得られるか | 入力値が正規化されて保存される |
| 異常系・エラー | 無効な入力が仕様どおり拒否または回復されるか | 不正な値がエラーになり、状態を変更しない |
| 境界 | 空、最小、最大、遷移、Unicode のケースでどうなるか | 空のラベルは定義済みの代替値になり、上限値は有効なまま |
| 状態・不変条件 | 操作の前後で何が維持される必要があるか | 更新失敗後も以前の値と無関係なレコードが保たれる |
| 回帰 | 報告された不具合を再現する最小の入力は何か | 以前クラッシュした形の入力が期待どおり処理される |

すべての関数に全分類のテストが必要とは限りません。期待動作や実装にその失敗要因がある場合に該当分類を含めてください。

同じルールを試す入力を何通りも列挙するのではなく、同値クラスを使います。複数の簡潔な入出力例が1つの動作を表すならパラメーター化し、別の準備が必要な場合や、異なる失敗理由を示す場合はテストを分けます。

## 構成と命名

Arrange–Act–Assert の流れを明確にします。

1. **Arrange:** シナリオに関係する状態だけを準備する。
2. **Act:** 対象の動作を1回実行する。
3. **Assert:** 重要な副作用の有無も含め、期待結果を確認する。

構成から明らかな場合、各段階のコメントは不要です。操作や重要なアサーションをヘルパーの中に隠さないでください。

実装メソッドではなく、テスト対象の単位と期待する動作を表す名前を付けます。そのファイル内の既存規約に従ってください。新しいテストでは条件を最後に置きます。

```text
<対象>_<期待する結果>[_when_<条件>]
```

コードベースで使われている名前の例:

- Rust: `answer_easy_graduates_new_card_to_review_queue`、`bury_leaves_suspended_card_untouched`、`add_or_update_notetype_preserves_usn_when_flag_is_set`
- Python/Qt: `test_update_collection_skips_backend_when_unchanged`、`test_is_audio_file_rejects_no_extension`

Vitest では識別子ではなく `test(...)` の説明文字列に動作を書きます（例: `test("event handler attributes are stripped")`）。

`test_helper`、`works`、`basic`、`case_1` のように、期待結果を説明しない名前は避けてください。

不具合の診断に十分な精度でアサーションします。単なる真偽値より、意味のある値や構造化された結果を比較してください。エラーは型またはバリアントを確認し、メッセージが安定していて利用者に関係する場合は内容も確認します。動作と関係のない書式や、必要なフィールドが一つだけなのにオブジェクト全体を比較することは避けてください。

## テストデータ、準備、後片付け

- 現実的な最小データを使い、`existing_record` や `invalid_name` のような意味のある名前を付けます。
- 周辺のテストで使われているビルダー、ファクトリー、フィクスチャを優先します。
- テスト固有の準備はテスト内に置きます。シナリオを見えにくくせずノイズを減らせる場合にだけヘルパーを抽出します。
- 一時ディレクトリ、一時コレクション/データベース、メモリ内の値を使います。ユーザーの Anki プロファイルを読み書きしないでください。
- パッチを当てたグローバル値、環境変数、タイマー、DOM 状態、コールバックを復元します。アサーションが失敗しても実行されるフレームワークの後片付け機能を優先します。
- テストは単独で、任意の順序で、繰り返し実行しても成功する必要があります。

## テストダブルと境界

実際に使える軽量で決定的な依存要素を優先します。時間、乱数、ネットワーク、サブプロセス、クリップボード、ネイティブダイアログ、バックエンド呼び出しなど扱いにくい境界を制御する場合に、スタブ、フェイク、スパイ、モックを使います。コードが依存先を参照する場所で差し替え、現実的な戻り値とエラーを返してください。

動作に関係するやり取りだけをアサートします。付随的な呼び出しや順序の確認は避けてください。すべての依存先をモックにし、呼び出しだけをアサートしているなら、役立つ動作ではなく実装をテストしている可能性があります。

## 時刻、乱数、並行処理、非同期動作

- 時刻が結果に影響する場合は、時刻を注入するか固定します。現在日付、ローカルタイムゾーン、日付変更時刻に依存させないでください。
- 乱数はシードを固定するか差し替え、偶然の結果ではなく不変条件を確認します。
- 正しさを待つために無条件の sleep を使わないでください。promise、コールバック、シグナル、タスク、条件を、上限時間を設けて待ちます。
- ユニットテストで正確な処理時間を要求しないでください。性能の主張は適切な許容範囲と環境制御を備えたベンチマークで確認します。
- ファイルやテストケースが並行実行されることを前提とします。変更可能なグローバル値、固定ポート、固定一時パスを共有しないでください。

## 回帰テスト

バグ修正には通常、その不具合を検出できるテストを含めます。

1. 報告を、代表的な最小の入力と状態に絞ります。
2. 不具合を再現し、期待動作を証明する最も低い層にテストを置きます。
3. 可能なら修正前のリビジョンで実行し、想定した理由で失敗することを確認します。
4. 修正を適用し、新しいテストが成功することを確認します。
5. 関連するテスト群を実行し、同種の問題が周辺にもないか確認します。
6. 回帰テストは残します。不具合番号ではなく動作を名前にし、テストだけでは表せない重要な背景がある場合に限り、短いコメントで課題へのリンクを追加します。

期待結果に不具合のある実装をそのまま記述しないでください。回帰テストは、将来のリファクタリングでも維持すべき動作を記述します。

## テストファースト

期待する動作が明確であれば、実装より先にテストを書く方法が有効です。テストが不具合を検出できることを確かめるのに役立ちます。

1. 期待する動作を確認する、焦点の絞られたテストを書く。
2. 想定した理由で失敗することを確認する。
3. 期待動作を満たす最小の本番コード変更を行う。
4. テストを成功させたままリファクタリングする。

テストファーストは必須ではありません。探索中や動作がまだ不明な場合は、まず期待動作を調べて説明します。バグ修正では、可能な限り修正前に回帰テストを失敗させることを強く推奨します。

## 追加で考慮するリスク

前述のシナリオ分類はすべての動作に適用されます。Anki 固有のリスクとして、次も検討してください。

- プロジェクト独自のシリアライズまたは変換コード
- 権限、パス、エスケープ処理、信頼できない入力との境界
- API の一部となるコールバック、シグナル、イベント、非同期完了
- 古いデータやアドオン向けに意図的に維持している互換動作

## テスト対象にしないもの

次の項目のためだけにテストを保守するのは避けてください。

- 観測可能な契約を持たない非公開の実装詳細
- 自明なコード、コンパイラーや型チェッカーで保証されること、生成アクセサー、サードパーティーの動作
- 同じルールをすべての言語層で網羅的に繰り返すこと
- レビュアーが正否を判断できないほど広いスナップショット
- 実ネットワークサービス、ユーザープロファイル、ホームディレクトリのファイル、マシン固有の実行ファイル
- 再現可能なシードや失敗例のない乱数入力
- モックで簡単に確認できるという理由だけの内部呼び出し回数
- より具体的な結果を確認できるのに、コードが実行された、真の値が返った、例外が出なかったことだけを証明するアサーション

## UI テストの範囲とコスト

Qt と Svelte のテストは、純粋なロジックのテストより準備と保守にコストがかかります。すべてのウィジェット、コンポーネント、プロパティ、マークアップをテストしようとしないでください。価値とリスクに見合う動作を UI テストで保護します。

優先してテストするもの:

- ロジック、ビューモデル、ストア、状態遷移、エラー処理
- 操作状態、シグナル、イベント、コールバック、バックエンド要求
- 利用者向け仕様に含まれるアクセシビリティロール、ラベル、フォーカス、キーボード操作
- 安定したユーザー可視動作の回帰

スタイル、正確な座標、偶発的な DOM 構造や CSS/Sass クラス名、アニメーション時間、プラットフォーム固有の描画、生成 UI コード、フレームワーク内部、大規模な UI スナップショットのユニットテストは避けます。

可能なら Qt ウィジェットや Svelte コンポーネントからロジックを抽出し、通常の Python または TypeScript/JavaScript としてテストします。UI 層のテストは、追加の確信につながる小規模な接続確認にとどめます。

表示の確認は UI レビューで行います。外観が安定した製品仕様であり、プロジェクトがその仕組みを採用している場合は、ビジュアル回帰テストも利用できます。コードが変わりやすいことだけを理由にテストを省略する必要はありません。実装と期待される表示の両方が一時的な場合は、壊れやすい UI テストを省く方がよいこともあります。

## 技術スタック別のガイド

以下の例は説明用の疑似コードです。`State`、`Model`、`normalize_value` などは Anki の API ではありません。実際のコードを確認せずにコピーしないでください。

### Python ライブラリ

Python ライブラリのテストは `pylib/tests/` に置き、`pytest` を使います。

- ファイル名と関数名は `test_*` にし、診断しやすい差分が得られる通常の `assert` を使います。
- 予期するエラーには `pytest.raises()` を使います。安定したメッセージが契約の一部であるか、精度向上につながる場合だけメッセージも照合します。
- 簡潔で同等なケースには `pytest.mark.parametrize()` を使います。
- 型付きフィクスチャ、`tmp_path`、`monkeypatch`、既存のコレクションヘルパーを優先します。リソースはフィクスチャやコンテキストマネージャーで閉じます。
- Python が所有するオーケストレーションや、現実的でないエラーをテストする場合に限り、Rust バックエンドをモックします。ドメインルールのテストを小さく見せる目的でモックしないでください。

一般的な例:

```python
import pytest


@pytest.mark.parametrize(
    ("raw_value", "expected"),
    [(" valid ", "valid"), ("", "default")],
)
def test_normalization_returns_the_documented_value(
    raw_value: str, expected: str
) -> None:
    assert normalize_value(raw_value) == expected


def test_invalid_value_is_rejected_without_mutating_state() -> None:
    state = State(value="existing")

    with pytest.raises(ValueError, match="invalid value"):
        state.update("invalid")

    assert state.value == "existing"
```

### Python/Qt

Python/Qt のテストも `qt/tests/` に置き、`pytest` を使います。

- フレームワークに依存しない判断は、まず通常の Python としてテストします。
- 必要最小限の Qt オブジェクトを作り、Anki ウィンドウ全体を起動しないでください。
- 公開操作または現実的な入力を行い、意味のある状態、シグナル、コールバック、バックエンド要求を確認します。シグナルの引数や回数が契約なら `QSignalSpy` またはコールバック記録用オブジェクトを使います。
- イベントループは、固定時間の sleep ではなく条件またはシグナルを上限時間付きで待ちます。
- ネイティブダイアログ、クリップボード、Web 要求、音声、バックエンド操作は境界で置き換えます。
- `QApplication`、メインウィンドウの状態、グローバルフックを分離し、後片付けします。

一般的な例:

```python
from unittest.mock import MagicMock


def test_submit_with_invalid_input_shows_error_without_saving() -> None:
    save = MagicMock()
    dialog = make_minimal_dialog(save=save)
    dialog.form.value.setText("invalid")

    dialog.accept()

    assert dialog.form.error.isVisible()
    save.assert_not_called()
```

### Rust

Rust のユニットテストは通常、コードの隣にある `#[cfg(test)]` モジュールに置きます。近くのクレートで使われているヘルパーと規約に従います。

- 大量のモックより、入力とアサーションを優先します。
- 診断しやすい差分を得るため `assert_eq!`/`assert_ne!` を使い、不変条件が自明でない場合はメッセージを付けます。
- 区別が重要なら `is_err()` だけでなく、期待するエラーバリアントまたは構造化された値を照合します。
- 型システムが保証するだけの性質ではなく、異なる動作をするバリアントや遷移を確認します。
- 永続化がテスト対象の場合だけコレクションを使い、それ以外では純粋なドメイン値を優先します。
- 1つの契約を確認する小さなテーブル駆動ループを使い、アサーションメッセージに入力を含めます。
- setup や、予期しないエラーがテスト失敗になるべき箇所では `unwrap()` と `expect()` を使えます。検証対象のエラーパスを調べるためには使わないでください。

一般的な例:

```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn empty_input_uses_the_default() {
        assert_eq!(normalize_value(""), "default");
    }

    #[test]
    fn invalid_input_preserves_existing_state() {
        let mut state = State::new("existing");

        let error = state.update("invalid").unwrap_err();

        assert!(matches!(error, UpdateError::InvalidValue));
        assert_eq!(state.value(), "existing");
    }
}
```

### Svelte、TypeScript、JavaScript

Web のユニットテストには Vitest を使います。現在の設定では、`ts/tests/e2e/` を除き、同じ場所にある `*.test.ts`、`*.spec.ts`、`*.test.js`、`*.spec.js` を検出します。

- 描画や操作で追加の契約を証明できる場合を除き、TypeScript/JavaScript のロジックと Svelte ストアを DOM なしでテストします。
- DOM API が必要な場合だけ `// @vitest-environment jsdom` を追加し、ドキュメントやグローバル状態を復元します。
- 外部境界では `vi.fn()`/`vi.spyOn()` を使い、タイマーに依存する動作にはフェイクタイマーを使います。どちらもテスト後に復元します。
- 実時間ではなく promise やリアクティブ更新を待ちます。表示をテストする場合は公開 UI を操作し、内部状態ではなくアクセシブルなロール、ラベル、表示テキストで検索します。
- 値や DOM に焦点を絞ったアサーションを優先します。構造全体が安定していてレビュー対象である場合に限り、小さなスナップショットを使います。
- 現在、リポジトリのユニットテストには専用の Svelte コンポーネント描画環境がありません。抽出したロジックや既存の DOM 環境でテストできない動作については、専用環境を独自に導入せず、適切な環境を相談するか、必要なブラウザー上の契約を既存の Playwright テストに配置します。

一般的な TypeScript の例:

```typescript
import { expect, test, vi } from "vitest";

test("invalid input reports the error without saving", async () => {
    const save = vi.fn();
    const model = new Model({ save });

    const result = await model.submit("invalid");

    expect(result).toEqual({ ok: false, reason: "invalid-value" });
    expect(save).not.toHaveBeenCalled();
});
```

Svelte コンポーネントでは、ユーザー操作と、画面またはアクセシビリティ上の結果で同じ契約を表します。無効な値を入力して送信し、エラーが表示され、保存されていないことを確認します。コンポーネントの非公開ハンドラーを直接呼び出さないでください。

## テストの実行と検証

リポジトリの `just` レシピを使います。

```sh
just test-rust  # Rust
just test-py    # Python ライブラリと Python/Qt
just test-ts    # TypeScript/JavaScript/Svelte のユニットテスト
just test       # すべてのスタック（Rust、Python、TS）
just check      # 必須の最終フォーマット、ビルド、lint、テスト検証
```

開発中は関連するスタックを頻繁に実行します。変更を完了する前に `just check` を実行してください。カバレッジの確認には[テストとカバレッジ](/developers/testing-coverage)、Playwright が必要な場合は[エンドツーエンドテスト](/developers/e2e-testing)を参照してください。

## レビューチェックリスト

テストが次の該当項目を満たすことを確認します。

- テスト名から、確認する動作が分かるか。
- その動作が成功する場合と失敗する場合が明確か。
- 重複を避けつつ、関連するシナリオ分類を最も適切な層で検討したか。
- Arrange–Act–Assert の流れが明確で、データが最小限であり、テストダブルを意味のある境界だけに使っているか。
- 決定的で、独立しており、後片付けされ、動作を保つリファクタリングに対して安定しているか。
- バグ修正の場合、可能なら修正前に回帰テストが失敗し、修正後に成功することを確認したか。
- 関連する `just` テストレシピと `just check` が成功したか。

## コーディングアシスタントへの指示

このドキュメントがコーディングアシスタントに渡された場合は、本番コードの動作、課題や差分、近くのテスト、利用可能なヘルパー、テストランナーの設定も確認してください。このガイドだけでリポジトリの状況を把握したことにはなりません。

編集前に要約を確認し、期待動作を説明して、担当する層を特定し、シナリオと選択したテストレベルを列挙します。その後、ローカルの命名規則、フィクスチャ、ビルダー、配置場所に従ってください。API、依存関係、フィクスチャ、ランナーの機能を捏造しないこと、非公開実装に到達する目的だけで本番コードの公開範囲を変更しないこと、テストを通すためにアサーションを弱めないこと。最後に、実行したテスト、意図的に省略したテスト、未検証の項目を報告してください。
