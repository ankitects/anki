---
title: "SonarCloud 解析"
---

SonarCloud は、静的解析とカバレッジに関する有用な結果を提供します。Quality Gate はマージに必須のチェックではありません。検出結果はレビューの参考に使われ、メンテナーの作業をブロックしません。このプロジェクトでは CI ベースの解析を使うため、自動解析は無効のままにしてください。

CI で実行されるテストコマンドとカバレッジのしきい値は、[テストとカバレッジ](/developers/testing-coverage)をご覧ください。

## 解析の対象

| イベント | 静的解析 | CI のカバレッジ | SonarCloud のカバレッジ |
| --- | --- | --- | --- |
| 内部のプルリクエスト | あり | あり | あり |
| `main` または `release/**` への push | あり | あり | あり |
| フォークからのプルリクエスト | あり | あり | なし |

フォークからのプルリクエストでも、権限を持たない CI ワークフローで、完全なテストカバレッジとカバレッジの低下チェックを実行します。レポートは権限を持つ SonarCloud ワークフローには取り込まれないため、SonarCloud はこれらの PR のカバレッジ指標を計算しません。

フォークのスキャンでも、静的なバグ、脆弱性、セキュリティ上の注意点、コードの臭いは報告されます。スキャナー側の Clippy とソフトウェア構成解析は無効です。Clippy は通常の CI チェックで引き続き実行します。

## 実行方法

`.github/workflows/sonar.yml` は CI ワークフロー全体が成功した後に実行されます。別のワークフローにすることで、コントリビューターのコードをビルドまたはテストするジョブから `SONAR_TOKEN` を分離できます。

1. ワークフローは GitHub API を使い、PR 番号、状態、head SHA、リポジトリ、ブランチを検証します。無効または古いコンテキストはブランチ解析として扱わず、安全に失敗します。
2. CI でテストした正確なコミットをチェックアウトします。フォークのソースコードはスキャナーが読み取るだけで、ビルド、インストール、ツールとしての実行はしません。
3. フォークがサーバーを変更したりビルドツールを有効にしたりできないよう、`sonar-project.properties` をデフォルトブランチの信頼できるコピーに置き換えます。解析するバージョンも、同じ信頼できるチェックアウトにある `.version` から取得します。固定のバージョンではなく、前回のリリース以降の新しいコードを計測します。
4. PR の場合、信頼できる上流リポジトリからターゲットブランチを取得し、`sonar.pullrequest.base` に渡す名前でローカルに固定します。SonarCloud は git から変更ファイルを判定するため、上流の正しい base 参照がないと、無関係な変更を PR に含める可能性があります。フォークのローカル base 参照は古いことがあります。この手順では解析対象コミット、base リポジトリとブランチ、base コミット、merge-base をログに記録し、参照を解決できない場合は安全に失敗します。
5. 内部の変更では、起動元の CI 実行からカバレッジ成果物をダウンロードします。フォークではレポートのパスを消去し、カバレッジ計算からのみすべてのソースを除外します。
6. `SONAR_TOKEN` を受け取るのはスキャナーのステップだけです。

## 信頼境界

<Warning>
    このワークフローは base リポジトリの `SONAR_TOKEN` にアクセスできます。ビルド、テスト、パッケージのインストール、PR から提供された設定、PR 内のローカル Action、復元された CI キャッシュを追加しないでください。特に、このワークフローから `just`、`cargo`、`npm`、`pip`、リポジトリのスクリプトを実行しないでください。
</Warning>

- 自動解析は無効のままにし、SonarCloud のチェックを必須にしないでください。
- `SONAR_TOKEN` はこのプロジェクトの解析だけに使えるよう制限してください。
- スキャナー側の Clippy とソフトウェア構成解析は無効のままにしてください。
- フォークが作成した成果物を、権限を持つスキャンに取り込まないでください。

フォークを解析するとき、スキャナーは信頼できないソースコードを解析します。これらの制約によって、コントリビューターのコードを直接実行するのを防ぎ、トークンの露出を抑えますが、サードパーティーの Action や解析ツールの脆弱性をなくすものではありません。
